# PM2 conformance

`tests/conformance/run.js` runs the same ecosystem file under PM2 and under
Vexor, each in an isolated home, and compares what a probe app experienced
(runs, argv, cwd, environment, instance numbers, stop signal) with what each
tool reported (status, restart count). Run it in a throwaway container with
`pm2` and `vexor` on PATH:

```sh
docker run --rm -v "$PWD/dist":/bin2 -v "$PWD/tests/conformance":/c:ro node:22-alpine \
  sh -c 'npm i -g pm2@7.1.0 && cp /bin2/vexor /usr/local/bin/ && node /c/run.js --out /bin2/report.md'
```

## Summary

Latest run: PM2 7.1.0 vs Vexor 0.1.1, 11 scenarios,
**10 identical, 1 intentional difference**.

The harness found two real incompatibilities in 0.1.0, both fixed for 0.1.1:

- `max_restarts: N` allowed N + 1 runs before errored; PM2 allows N.
  `max_restarts: 0` now means PM2's default, 16.
- Graceful stop sent SIGTERM; PM2 sends SIGINT. Vexor now sends SIGINT
  by default, and the new `kill_signal` setting chooses another signal.

### Intentional difference: `wait_ready` without a ready signal

When `listen_timeout` expires and the app never called `process.send('ready')`,
PM2 marks the app **online** anyway. Vexor treats it as a **failed start**
(stopped, counted against `max_restarts`, restarted with backoff; errored when
the budget runs out), so a broken app is never reported healthy and a reload
never retires a working process in favour of one that never became ready.

### Not compared

Vexor limits automatic restarts to one per second per instance, while PM2
restarts immediately with `restart_delay: 0`. The final counts match (see
`crash-budget-0`), but Vexor reaches them more slowly; the harness waits long
enough for both.
